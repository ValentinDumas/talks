A notable case where rewriting legacy code was the better option is Cars.com's decision to completely retool their systems for a modern cloud infrastructure using Elixir and Phoenix. This rewrite was driven by several strategic factors: their legacy system used outdated technologies that made it difficult to attract and retain developers, and the accumulated technical debt was so substantial that it outweighed the value of the existing business logic. By rewriting, Cars.com was able to realign their technical team with a modern software development culture and better support their next generation of products.

This example highlights key reasons when rewriting is preferable:

The legacy system relies on outdated technologies that hinder developer onboarding and retention.

The project scope has evolved so much that the original codebase no longer fits current business goals.

Technical debt has grown too large for incremental refactoring to be effective.

Rewriting in such scenarios can eliminate technical debt, leverage modern technologies and architectures, and ultimately produce a more maintainable, scalable, and performant system than a patchwork refactor would allow.
